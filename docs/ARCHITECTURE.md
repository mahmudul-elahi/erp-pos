# Architecture

Status: Phase 0 baseline, approved decisions pending.
Last updated: 2026-11-09.

This document describes how the POS + e-commerce + light ERP backend is
structured. The product specification remains the source of truth for business
requirements. Where the repository forces a deviation, it is recorded here and
in `BUSINESS_DECISIONS.md`.

## 1. Context

The system is a modular monolith built with NestJS and TypeScript. It serves a
Bangladeshi electronics/gadget business with multiple branches, warehouses and
sales channels. Money, stock and audit history are the highest-risk areas, so
the architecture optimises for correctness, traceability and clear module
boundaries before premature service extraction.

## 3. Modular monolith

Use one deployable NestJS application. Do not introduce microservices until a
measured scaling or deployment need exists. Module boundaries must remain
extractable later:

- A feature module owns its tables and business rules.
- Controllers handle HTTP only: routing, DTO binding, status codes.
- Services implement use cases and transactions.
- Repositories/data-access providers own Prisma queries.
- Cross-module reads go through exported services or explicitly shared
  read-model providers, not by reaching into another module's tables.
- Critical stock and money changes stay inside one database transaction. Events
  are for side effects, not for committing the source of truth.

## 5. Layering and dependency rules

```text
HTTP controller
  -> DTO validation / guards / interceptors
  -> application service (transaction boundary)
  -> repository or data-access provider
  -> Prisma client
  -> PostgreSQL
```

Rules:

- No business logic in controllers.
- No Prisma calls from controllers.
- Services may call other modules' exported services, never their repositories.
- Infrastructure modules (`minio`, `redis`, `queue`, `mail`, `payments`,
  `couriers`) expose narrow interfaces; business modules do not depend on SDK
  details.
- Shared code lives in `common/` only when it is genuinely generic.
- Avoid circular module imports; use events only for non-critical side effects.

## 6. Cross-cutting conventions

- **Configuration:** validated at startup; fail fast with a readable error.
- **Validation:** DTOs with `class-validator` and `class-transformer` (spec
  requirement), `whitelist`, `forbidNonWhitelisted`, `transform`.
- **Responses:** global interceptor wraps success responses as
  `{ success, message, data, meta? }`.
- **Errors:** global exception filter returns
  `{ success: false, message, errorCode, details? }`; no stack traces in
  production.
- **Pagination:** shared `page`, `limit`, `sortBy`, `sortOrder`, `search`
  DTOs; cap `limit`.
- **Request context:** correlation/request id, authenticated actor, branch
  scope and IP stored in `AsyncLocalStorage`.
- **Logging:** structured `nestjs-pino` logs with redaction of passwords,
  tokens, authorization headers, payment secrets and full customer contact
  data.
- **Audit:** `AuditLog` records privileged actions (refunds, discounts, stock
  adjustments, status overrides, cash withdrawals, permission changes).

## 7. Data and financial integrity

- Use Prisma migrations; never `db push` for shared or production databases.
- Use database transactions for sales, purchases, returns, transfers,
  refunds, payments and cash transfers.
- Use `Decimal` for money and `decimal.js` for arithmetic. Never `number` for
  financial totals.
- Store price and cost snapshots on transaction line items.
- Stock is derived from immutable `StockMovement` rows; `InventoryBalance` is
  a transactionally maintained cache that can be reconciled.
- Every stock change writes a movement in the same transaction.
- Never hard-delete completed sales, payments, stock movements or ledger
  entries. Use reversal/adjustment records with reasons.
- Use `SELECT ... FOR UPDATE` or atomic conditional updates for contended
  stock rows. Never allow stock to go negative unless the business explicitly
  enables backorders.
- Unique constraints protect SKUs, barcodes, serial numbers, document numbers
  and idempotency keys.
- Master data may use soft delete (`deletedAt`); financial and stock history
  must not.

### Transfer accounting rule (proposed)

`InventoryBalance` tracks `onHand`, `reserved` and `inTransit` per warehouse.

- Dispatch: source `onHand -= qty`; destination `inTransit += qty`.
- Receive: destination `inTransit -= qty`; destination `onHand += qty`.
- Cancel after dispatch: destination `inTransit -= qty`; source `onHand += qty`.
- A unit is never counted in both `onHand` and `inTransit`.

This rule must be tested in Phase 4 before transfers are exposed.

### Order reservation rule (proposed)

- Reserve stock when an order reaches `Confirm` or `Approve`.
- Deduct stock when the order is dispatched/completed, according to the
  fulfilment policy.
- Release the reservation on cancellation, rejection or expiry.
- The exact status is configurable and must be confirmed in Phase 7.

## 8. Authentication and authorization

- Argon2id password hashing.
- Short-lived JWT access token and rotating refresh token.
- Refresh tokens stored as hashes only, with family/rotation/revocation
  tracking.
- Permission-based RBAC, not hard-coded role names.
- Permissions use namespaced strings such as `products.create`,
  `sales.refund`, `inventory.adjust`, `reports.view`, `users.manage`.
- Branch scoping: `UserBranch` membership; super admin bypasses branch
  restrictions. Branch staff only see assigned branches unless explicitly
  granted broader access.
- Rate limit login, password reset, public verification and upload URL
  creation.
- Guards: authentication, permissions, branch scope. All three must be
  covered by tests.

## 9. File storage

- MinIO is the only object storage provider initially.
- One private bucket (`MINIO_BUCKET`); clients receive short-lived presigned
  upload/download URLs.
- The backend never exposes MinIO credentials.
- `files` table stores object key, bucket, MIME type, size, extension,
  uploader, module, entity association and timestamps.
- Object keys are generated: `module/{entityId}/{purpose}/{uuid}.{ext}`.
- Prefer presigned uploads. On completion, verify object existence, size and
  actual content type (magic bytes, not the client's claim) before persisting
  the file record.
- Allowlist MIME types and extensions per use case; reject executables.
- Private documents use short-lived download URLs.
- Bucket creation belongs to deployment/setup, not application startup.

## 10. API conventions

- Base path: `/api/v1`.
- Swagger: `/api/docs`, bearer auth configured.
- Success envelope:

```json
{
  "success": true,
  "message": "Products retrieved successfully",
  "data": [],
  "meta": { "page": 1, "limit": 20, "total": 0, "totalPages": 0 }
}
```

- Error envelope:

```json
{
  "success": false,
  "message": "Validation failed",
  "errorCode": "VALIDATION_ERROR",
  "details": []
}
```

- Use appropriate HTTP status codes.
- All list endpoints support pagination, filtering, sorting and search.
- Idempotency keys are required for payment callbacks, courier webhooks and
  retryable job creation.

## 11. Jobs and events

- BullMQ on Redis for courier shipment creation, tracking sync,
  notifications, report exports, low-stock notifications and reconciliation.
- Jobs must be idempotent, have bounded retries with backoff, log a
  correlation id, and never log secrets or full personal data.
- Failed jobs must be inspectable and replayable.
- In-process events (`@nestjs/event-emitter`) are for non-critical
  decoupling only. Stock and money updates happen in the database transaction.

## 12. Testing

- Unit tests for services and pure business rules.
- Integration tests against real PostgreSQL for transactional workflows.
- E2E tests with Supertest for API flows and permissions.
- Concurrency tests for stock and checkout.
- Idempotency tests for webhooks and jobs.
- Test runner: Vitest (scaffold default). Supertest remains the HTTP client.
- Test database is separate from the development database; migrations run
  before integration/E2E suites, and data is isolated per test.

Critical scenarios are listed in the product specification and must be
implemented as tests when their phase is reached.

## 13. Deployment

- `docker-compose.yml` provides local PostgreSQL, Redis and MinIO.
- Add an application `Dockerfile` in Phase 1 once Prisma/config are in place.
- Production uses managed PostgreSQL/Redis and S3-compatible storage; MinIO
  console and database are never public.
- HTTPS terminates at the reverse proxy.
- Backups and a documented restore procedure are required before go-live.
- Secrets come from environment variables or a secret manager, never source
  control.
